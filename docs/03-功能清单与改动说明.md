## 一、原有功能（改造前）

> ⚠️ **本章描述的是改造前的老平台**，里面提到的「企业」角色**已经删除了**。
> 现在平台只有**学生 / 老师 / 管理员**三端，改造后的口径见第三章和 `11-小组与答辩意见改造记录.md`。
> 保留这一章是为了说明「哪些是老功能」和「改了哪些」。

功能来自原平台源码实证（13 个 Controller、21 张表、30 个前端页面），不是照操作指南抄的。

### 1.1 账号体系

| 功能 | 说明 |
|---|---|
| 三种角色 | 学生、企业、管理员 |
| 注册 | 账号至少 4 位；密码至少 8 位，须含大小写字母+数字+特殊字符 |
| 注册审核制 | 注册后 audit_status=0，管理员审核通过才能登录 |
| 找回密码 | 通过账号+邮箱重置 |
| 管理员账户审核 | 待审核/已通过/已拒绝三个列表 |
| 账号启用禁用 | 管理员可禁用捣乱账号 |

### 1.2 内容填写（双向）

| 功能 | 说明 |
|---|---|
| 学生发「项目」 | 标题、地区、标签、描述（≤3000字）、附件、预算、起止日期 |
| 企业发「需求」 | 标题、地区、标签、描述、附件、预算、紧急程度、期望完成日期 |
| 填写审核制 | 填写后 status_id=1（待审核），管理员通过才上线 |
| 我填写的 | 看自己填的内容和审核状态 |

### 1.3 对接流程

| 功能 | 说明 |
|---|---|
| 浏览合作 | 看所有已发布内容（状态词，非动作）|
| 对接规则 | 学生只能申请企业发的需求；企业只能对学生项目表达意向；同类不能互发 |
| 提交申请 | 填申请原因 + 联系方式 |
| 我的申请-我发出的 | 看 已通过/已拒绝 |
| 我的申请-我收到的 | 通过 / 拒绝，可填回复 |

### 1.4 其他

| 功能 | 说明 |
|---|---|
| 消息中心 | 审核结果、收到申请的通知 |
| 附件上传 | 总 1024MB，单文件 100MB |
| 标签库 | 后台维护，填写时选择 |

## 二、新增功能（本次改动）

### 2.0 业务模型改造：小组 + 答辩意见（最新一轮，最重要）

> 详细记录见 `11-小组与答辩意见改造记录.md`，方案讨论见 `10-业务模型改造方案（待确认）.md`。

#### ① 名称口径：全部「发布」→「填写」

| 项 | 说明 |
| --- | --- |
| 改了什么 | 界面上所有「发布」字样改成「填写」：菜单「我的发布」→「我填写的」、按钮「发布新内容」→「填写信息」等，共 16 个前端文件 |
| 没改什么 | 代码标识符（`PublishProject.vue`、`publishArticle()`）、接口路径（`/blog/article`）、表名、以及状态词「已发布」 |
| 为什么 | 学生交上来的是**填写的信息**，不是「发布」出去的内容。只改给人看的字，避免牵连后端 |

#### ② 小组（一个小组只能有一个项目）

| 功能 | 说明 |
| --- | --- |
| 建组 | 组长可自建；**管理员可代建**（可指定组长为他人） |
| 成员 | 分**组长 / 组员（学生）/ 指导老师**三类 |
| 拉人 | 组长邀请 → **对方同意**才进组；**管理员可直接拉**，无需同意 |
| 指导老师 | 可一开始没有，后续添加；管理员也能加 |
| 唯一性 | **一个小组只能有一个项目**，用库层面 `uk_group_article` 唯一索引卡死 |
| 组长权限 | 改组信息、邀请成员、移除成员、转让组长、设答辩意见可见范围、解散小组 |

**位置**：
- 后端 `ai-collab-blog` 的 `BlogGroup` / `BlogGroupMember` / `IBlogGroupService` / `BlogGroupServiceImpl`
- 接口 `admin/openapi/blog/BlogGroupController.java`
- 前端 `views/cooperation/MyGroup.vue`、`views/admin/GroupManage.vue`、`api/group.js`

#### ③ 答辩意见（答辩现场老师方/专业方的问题与意见）

| 功能 | 说明 |
| --- | --- |
| 来源 | **管理员上传**（学生不能传），内容是答辩时老师方、专业方给出的问题和意见 |
| 录入方式 | ① 单条添加；② **表格批量导入**（整理成 CSV 一次导入一批，空行自动跳过） |
| 资料 | 可上传文档/表格，也可只记文字（正文和附件至少有一个） |
| 归属人 | 用**自由文本**记来源（如「张老师」「校外专家」），不关联真实账号 |
| 通知 | 上传后**组内全体成员**收到站内通知 |
| 可见性 | **组员和指导老师永远看全部**；组外人员由组长设置 |

**可见性三档（组外人员的可见程度）**：

| 档位 | 组外能看到 |
| --- | --- |
| 仅组内 | 什么都看不到（列表里根本不出现） |
| **可见摘要（默认）** | 标题 + 来源 + 正文前 50 字；**附件不下发** |
| 可见全部 | 完整正文 + 附件 |

**两级设置**：组长可设**全局默认**（管整个小组），也可对**单条覆盖**（改某一条）。

**位置**：
- 后端 `ai-collab-blog` 的 `BlogOpinion` / `IBlogOpinionService` / `BlogOpinionServiceImpl`
- 接口 `admin/openapi/blog/BlogOpinionController.java`
- 前端 `views/admin/OpinionManage.vue`、`components/OpinionList.vue`、`api/opinion.js`

#### ④ 顺手补的一个接口（原设计遗漏）

`GET /user/find/list` —— 按账号/昵称搜人。

**问题**：组长邀请成员时要在界面上搜人，但原来的搜人接口 `/root/user/list` 是
**管理员专属**的（`/root/*` 前缀），学生和老师调不了。

**做法**：新开一个轻量接口，只返回 id / 账号 / 昵称 / 头像，
**邮箱和手机号一律不给**，且只放行已审核通过、已启用的账号。

**位置**：`admin/openapi/user/UserFindController.java`

#### ⑤ 为下一轮「视频」预留的字段

本轮不做视频，但**字段位置已留好**，下轮不用再动表结构：

`blog_article_info.video_url` / `video_cover`、`blog_opinion.video_url`

下一轮要补的见 `11-…改造记录.md`。

### 2.0.5 第二轮改造：申请表单 + 临时通道 + 老师完善

> 详细记录见 `11-小组与答辩意见改造记录.md` 第十节。

#### ① 申请表单：改成「年级 + 班级 + 擅长」

| 项 | 改造前 | 改造后 |
| --- | --- | --- |
| 必填 | 申请原因（≥10字）+ 联系方式 | **年级 + 班级 + 擅长部分** |
| 年级 | — | 下拉（22~26级） |
| 班级 | — | 下拉，**随年级联动** |
| 擅长 | — | **多选预设技能**（13 项：前端/后端/移动端/数据分析/AI/硬件/UI/文档/PPT/视频/测试/运维/调研） |
| 申请原因 | 必填 | 改名「补充说明」，**选填** |
| 联系方式 | 必填 | **选填**（有临时通道了，不必先互换微信） |

**改动理由**：组长审核申请时最关心的是「这人是哪个班、会干什么」，
而不是一段客套的理由。原来是逼着申请人写客套话。

#### ② 老师也能填写内容

| 项 | 说明 |
| --- | --- |
| 老师发什么 | 「**项目想法**」——有兴趣的学生可以探讨和申请 |
| 和学生的区别 | **不强制建小组**（老师不必先组队） |
| 存哪 | 和学生项目**同一张表、同一类型**，只是发布者角色不同 |
| 列表标识 | 标题旁显示橙色「**老师发布**」标签，学生一眼能分辨 |

#### ③ 临时沟通通道（全新一套，和站内会话并存）

| | 站内会话 | **临时通道** |
| --- | --- | --- |
| 形态 | 登录后在「站内沟通」里 | **一条链接** `/tmp-room/{token}` |
| 生命周期 | 一直在 | **有有效期，到期自动失效** |
| 访问 | 必须登录 | **凭链接可看，发言才要登录** |
| 建立时机 | 申请通过后 | 申请通过后**自动开通** |

**为什么要两套**：临时通道解决「先聊聊看」这个场景 ——
不用加微信、不用互换联系方式，给个链接就能谈；谈成了再走正式流程。

**安全设计**：token 随机不可猜；到期或关闭后立即失效；外部人拿到链接能看不能发言。

### 2.0.7 第三轮改造：用户反馈的 5 个问题

> 详细根因和排查过程见 `11-小组与答辩意见改造记录.md` 第十一节。

| # | 问题 | 改成什么样 |
| --- | --- | --- |
| 1 | 管理端「用户角色分布」有误 | 原来只统计学生和企业、老师没算，第四块还是减法凑的「管理员/其它」。**现在三档**：学生 / 老师 / 管理员 |
| 2 | 学生端看不到答辩意见的修改入口 | 组长现在可以**逐条**设可见范围（原来只能设全组默认），每条旁边显示当前范围和「（单独设）」标记 |
| 3 | 注册页还是「企业」 | 第二个身份改成「**老师**」，字段从「企业全称 + 所属行业」换成「**所属学院 + 职称**」 |
| 4 | 邮箱不该必填 | 改成**选填**（前端校验 + 后端注解 + 数据库约束三层一起放开） |
| 5 | 企业全称要去掉 | 个人资料、账号管理、账号审核、个人主页四处全清 |
| — | （顺手修）老师点不到「感兴趣」 | 列表页和详情页都带着老规则（学生只能申请需求、老师直接 `return false`），老师在整个平台都点不到。已改成**学生和老师都能对别人的内容表达兴趣** |

**「感兴趣」现在的规则**：只要是别人填的内容，学生和老师都能点；自己填的不能申请。
提交后由发布者决定，通过后自动开通临时沟通通道。

### 2.0.8 第四轮改造：「感兴趣」按角色分两种表单

> 详细记录见 `11-小组与答辩意见改造记录.md` 第十二节。

| 角色 | 必填 | 选填 |
| --- | --- | --- |
| 学生 | 年级 + 班级 + 擅长部分 | 补充说明、联系方式 |
| 老师 | **为什么感兴趣** + 联系方式 | — |

老师的表单里完全不出现年级 / 班级 / 擅长。

**顺带修掉一个老 bug**：项目里有两个同名的 `BusinessException`
（`exception` 包和 blog 模块自带的 `models.common` 包），全局异常处理器只接了前一个 ——
后果是 **blog 模块所有业务提示都被吞成「服务器开小差了」**，
用户从来没见过「不能对自己发布的内容发起申请」这类真正的原因。已在处理器里补上。

### 2.0.9 第五轮改造：头像位置 + 两个红点联动已读

> 详细记录见 `11-小组与答辩意见改造记录.md` 第十三节。

**头像位置**：长期会话页原来用 `flex-direction: row-reverse` 反转整行，导致**自己的头像跑到了最左边**。
改用 `justify-content: flex-end` —— DOM 顺序不动，自己的消息靠右，头像自然在文字右侧。
临时通道页原来压根没头像，一并补上。

**两个红点联动**：消息中心和站内沟通的红点数的是**两张不同的表**
（`notice_box_info` / `chat_message`），所以原来读完聊天，消息中心那条「收到一条新消息」还挂着未读。

改法：
- 给通知表加 `ref_id` 字段，把会话消息类通知**关联到具体会话**
- 读完会话 → 只清该会话的通知（**精确联动**，别的会话不受影响）
- 消息中心「全部已读」→ 连带清掉聊天未读
- 前端加 `unreadBus` 全局信号，**操作完立刻刷新红点**（不用等 60 秒轮询）

### 2.0.10 第六轮改造：找回密码改成手机号

> 详细记录见 `11-小组与答辩意见改造记录.md` 第十四节。

**需求**：用户先提「邮箱改必填，因为找回密码需要」，后改口「能不能用手机号找回」——
最终定为：**找回密码走手机号，手机号注册必填，邮箱恢复选填**。

**为什么手机号更好**：手机随身带不容易忘；`phone` 列本来就有唯一索引能唯一定位；
学生注册留的手机号比邮箱真实。

**前提**：手机号必须同时改成**必填** —— 否则没填手机号的账号照样找回不了。
（这和「邮箱必填」是同一个逻辑：**找回凭据必须人人都有**。）

**顺带修掉一个老 bug**：找回密码页提交的字段名是 `password`，后端要的是 `newPassword` ——
**这个功能从来就没成功过**。因为错误被前端拦截器统一提示成「服务器开小差了」，一直没被发现。

**安全设计**：「账号不存在」和「手机号不对」返回**同一句提示**，防止有人拿接口试探账号是否存在。

### 2.2 中价值改动（第二梯队）

#### ⑥ 站内会话（最重要的一项）

**问题**：这是平台最大的断点——**申请通过后就断了**。
双方只能靠申请时留的微信号线下联系，平台里没有任何沟通渠道。等于平台只负责「牵线」，牵完就不管了。

**改动**：
- 新表 `chat_session`（会话）+ `chat_message`（消息）
- 对接申请通过后，系统自动创建两人会话
- 会话列表（左侧）：显示对方头像、名字、最后一条消息、未读数
- 聊天区（右侧）：气泡式对话，自己的消息靠右，对方靠左
- 支持 Ctrl+Enter 发送
- 未读消息自动标记已读
- 顶部导航显示未读角标

**位置**：
- 后端 `ai-collab-notice` 模块的 `IChatService` / `IChatService` 实现
- 前端 `views/cooperation/ChatCenter.vue`

---

#### ⑦ 对接进度状态流转

**问题**：原来只有「已通过/已拒绝」两态。申请通过后项目进行到哪了，没人知道。

**改动**：新增 `collab_progress` 字段，6 个状态：
```
0 待处理 → 1 已通过 → 2 洽谈中 → 3 已合作 → 4 已结束
                    ↘ 5 已拒绝
```
申请人和组长双方都能推进进度，我的申请页可直接「更新进度」。

**位置**：`blog_registration.collab_progress` 字段 + `views/cooperation/MyApplications.vue`
