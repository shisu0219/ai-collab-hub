### 业务规则（写在 `BlogGroupServiceImpl`）

1. **一个人只能带一个小组**（建组时校验，防止一个组长对应多个项目）
2. **组长自己也写一条成员记录**（`member_role=1`）—— 这样「组内成员」判断逻辑统一，不用到处特判
3. **重复邀请不新增记录，改状态**（表上有唯一索引，硬插会报错）
4. **组长不能被移除**，要换人走 `transferLeader`
5. **不能通过邀请产生第二个组长**（`memberRole=1` 被拒绝）
6. **管理员代建时可以指定组长**，且一并拉进来的成员直接生效、不用同意

## 4.2 可见性规则（本模块核心）

```
组长 / 组员 / 指导老师  →  全部可见（无条件）
管理员                 →  全部可见
────────────────────────────────────────
组外人员 → 按 scope 取值：
    0 仅组内    → 列表里根本不出现；直查详情报「这条答辩意见仅小组内可见」
    1 可见摘要  → 正文截断到 50 字 + 加省略号，truncated=true，附件不下发
    2 可见全部  → 原样返回

取值优先级：scope_override（单条） > blog_group.opinion_scope（全局默认）
```

**⚠️ 三条重要注意事项**

1. **过滤做在后端 Service，不在前端。** 前端藏按钮不算数 —— 别人直接调接口还是能拿到。
   实测：用组外账号 curl 打接口，仅组内档返回 0 条、直查详情被拒。

2. **摘要模式下附件地址不下发。** 否则「正文截断」就白做了 —— 直接下载资料即可绕过。

3. **上传人昵称在 admin 层回填。** blog 模块依赖不到 sys 模块，拿不到用户表。

### 批量导入（你选的方案 C）

管理员把答辩记录整理成表格 → 另存为 **CSV** → 前台上传解析 → 一次性提交。

**为什么用 CSV 不用 xlsx**：前端不用引第三方解析库（`xlsx` 包体积大），
而 Excel / WPS 都能「另存为 CSV」，管理员操作成本几乎一样。

CSV 模板列顺序：`类型,标题,正文,来源`（第一行表头自动跳过）。
类型支持中文「答辩问题/答辩意见/修改建议」。

**实测**：空行会被跳过（3 行里 2 行有数据 → 导入 2 条）。

## 6.6 后验发现并修复的真 bug（Pitfall）

**现象**：组长把某条意见设成「仅组内 / 可见全部」后，再点「恢复跟随全局默认」，
接口返回 `200 设置成功`，但**那条意见的可见性一点没变**。

**根因**：

```java
// 错的写法
op.setScopeOverride(scope);   // scope 传 null 表示"跟随全局"
op.setUpdateBy(operatorId);
updateById(op);               // ← MyBatis-Plus 默认 NOT_NULL，null 字段不进 SQL
```

MyBatis-Plus 的 `updateById` 默认字段策略是 `NOT_NULL` —— **值为 null 的字段不会出现在
UPDATE 语句里**。所以「恢复跟随全局」这个操作**静默失效**：不报错、不抛异常、返回 200，
只有查库才看得出这一列没变。

**修法**：

```java
// 对的写法
baseMapper.update(null, new LambdaUpdateWrapper<BlogOpinion>()
        .eq(BlogOpinion::getId, opinionId)
        .set(BlogOpinion::getScopeOverride, scope)      // 显式 set，null 也写进去
        .set(BlogOpinion::getUpdateBy, operatorId));
```

外加：`import com.baomidou.mybatisplus.core.conditions.update.LambdaUpdateWrapper;`
（是 `update` 包，不是 `query` 包）；用继承来的 `baseMapper`，不是自己造的 `xxxMapper` 字段。

**验证**：修复前 `scope_override` 从 2 清不掉；修复后同一条变成 `NULL` ✅。

**为什么差点漏掉**：这个 bug 是被抽验脚本的**不稳定**暴露出来的 ——
脚本没清残留，导致第 2 轮断言失败。**第一反应是「测试脏数据」，差点手工清一下就过。**
顺着查发现「清理代码执行了、接口返回 200、但库里没变」，才定位到是真 bug。

**所以抽验脚本加了两条纪律**：
1. **开头先复位前置状态**（把所有单条覆盖清成 NULL），保证起点干净
2. 断言失败时**先查库确认数据到底改没改**，再判断是脏数据还是代码 bug
3. 验证完**连跑 2~3 轮**确认可重复（本轮实测连跑 3 轮均 46/46）

## 10.4 临时沟通通道（本轮最大的新增）

### 和站内会话的区别（别搞混）

| | 站内会话 `chat_session` | 临时通道 `tmp_room` |
| --- | --- | --- |
| 形态 | 长期会话 | 临时房间 |
| 入口 | 登录后「站内沟通」列表 | **链接** `/tmp-room/{token}` |
| 生命周期 | 一直在 | **有有效期，到期自动失效** |
| 建立时机 | 申请通过后（原有逻辑） | 申请通过后**自动开** |
| 访问 | 必须登录 | **凭链接可看，发言才要登录** |

**两套并存、互不影响。** 语义不同：正式合作走会话，先聊聊看走临时通道。

### 数据库

新增两张表：

```sql
tmp_room          房间：room_token / user_a / user_b / status / expire_time / registration_id
tmp_room_message  消息：room_id / sender_id / content
```

### 接口

| 方法 | 路径 | 权限 |
| --- | --- | --- |
| GET | `/tmp/room/enter?token=xxx` | **免登录**（凭链接查看） |
| GET | `/tmp/room/messages?token=xxx` | **免登录**（凭链接读消息） |
| POST | `/tmp/room/message` | 需登录 + **须是参与人** |
| POST | `/tmp/room/close` | 参与人 |
| POST | `/tmp/room/extend` | 参与人（续期） |
| GET | `/tmp/room/my` | 登录用户 |
| GET | `/tmp/room/by-registration/{id}` | 登录用户 |
| GET | `/tmp/room/by-article/{id}` | 登录用户 |
| POST | `/tmp/room/create` | 登录用户（过期后补开） |

### 三个关键设计

1. **token 用 `SecureRandom` 生成 24 字节再做 URL 安全 Base64**，不可猜、不会撞。
   **不要改成自增ID或时间戳拼的** —— 那等于把房间大门敞开。

2. **判断房间可用必须 `status` + `expireTime` 一起看**：
   - `status=0` 是被人手动关的（可能还没到点）
   - `expireTime < now` 是到点自动失效的（`status` 可能还是 1）
   **只看一个就会漏。** 实现在 `requireUsableRoom()`，所有入口都调它，保证判断一致。

3. **免登录能看、发言必须登录且必须是参与人**。
   不然拿到链接的人都能冒充身份说话。

### 默认有效期

72 小时。可续期（从「现在」或「原到期时间」取较晚的那个往后延，避免过期房续期后反而变短）。

### 第 4 条最值得说：必填往往是三层的

一开始只改了前端校验和 DTO 注解，**实测注册直接 500**：

```
Field 'email' doesn't have a default value
```

数据库那层 `NOT NULL` 还在。改法是：

```sql
ALTER TABLE sys_user MODIFY COLUMN email VARCHAR(128) NULL COMMENT '邮箱（选填）';
```

> 保留 UNIQUE 索引 —— MySQL 的 UNIQUE **允许多个 NULL**（NULL != NULL），
> 所以多个人都不填邮箱不会冲突，填了的仍然不能重复。

**以后再遇到「某个字段要改必填/选填」，记住查三层**：
前端 rules → 后端 DTO 注解 → 数据库列约束。少查一层就是运行时 500。

```js
return myRole === 'STUDENT' || myRole === 'TEACHER' || myRole === 'ENTERPRISE'
```

## 11.3 答辩意见单条可见性（本轮新增能力）

### 两级设置的关系

```
blog_group.opinion_scope        全组默认（组长设一次，管全组）
blog_opinion.scope_override     单条覆盖（NULL = 跟随全局）
```

取值 `0仅组内` / `1可见摘要` / `2可见全部`。**单条有值时覆盖全局。**

### 前端入口

组长在每条意见右侧看到：

- 当前生效范围的状态标签（`仅组内可见` / `组外可见摘要` / `组外可见全部`）
- 单独设过的会带「（单独设）」后缀

### 为什么 `OpinionVO` 必须有 `scopeOverride`

`effectiveScope` 是**算完的结果**，分不出这两种情况：

- 全局默认 = 1，这条单独设成 1（其实设过）
- 全局默认 = 1，这条没设过（跟随默认）

前端要显示「（单独设）」标记、回显时也知道该用哪个值，所以必须把原始覆盖值也给出来。

### ⚠️ 一个验证上的坑

`scopeOverride` 为 `null` 时，**Jackson 配了 `NON_NULL` 就不输出这个键**。
所以断言「返回体必须有 scopeOverride 键」会误报失败 ——
**正确验法是：先设一个值，看它出不出来**。本项目实测确认了这个行为。

# 十二、第四轮改造：「感兴趣」表单按角色分两种 + 修掉一个吞异常的坑

## 12.1 需求

> 用户原话：「感兴趣的环节，老师不需要填写年级班级和擅长什么部分，只需要写为什么感兴趣和联系方式」

| 角色 | 必填 | 选填 |
| --- | --- | --- |
| 学生 | 年级 + 班级 + 擅长部分 | 补充说明、联系方式 |
| 老师 | **为什么感兴趣** + 联系方式 | — |

老师的表单里**完全不出现**年级 / 班级 / 擅长。

**为什么老师不填年级班级**：老师本来就是教课的，「几年级几班」对学生才有意义。
老师申请时，发布方关心的是「他想干什么、怎么联系」，不是他的班级。

## 12.2 改动点

### 前端 `ProjectDetail.vue`

```vue
<!-- 学生：年级 / 班级 / 擅长 -->
<template v-if="!isTeacher"> ... </template>
<!-- 老师：只填为什么感兴趣 -->
<template v-else>
  <el-form-item label="为什么感兴趣" prop="reason"> ... </el-form-item>
</template>
```

校验规则从**静态对象**改成 **computed**（能随角色变）：

```js
const applyRules = computed(() => {
  const base = {
    contactWayValue: isTeacher.value
        ? [{ required: true, message: '请留下联系方式，方便对方联系你', trigger: 'blur' }]
        : []
  }
  if (isTeacher.value) {
    return { ...base, reason: [{ required: true, message: '请说说你为什么感兴趣', trigger: 'blur' }] }
  }
  return { ...base, grade: [...], className: [...], skills: [...] }
})
```

提交时老师不传那三项（传空字符串，后端按「未填」处理）。

### 后端校验也要分角色

`BlogRegistrationServiceImpl.submitRegistration` 原来是写死的：

```java
if (StrUtil.isBlank(dto.getGrade()) || StrUtil.isBlank(dto.getClassName())) {
    throw new BusinessException("请填写你的年级和班级");
}
```

**老师不填年级班级，会被这段拦死**。改成：

```java
if (isTeacher) {
    if (StrUtil.isBlank(dto.getReason())) {
        throw new BusinessException("请填写你为什么感兴趣");
    }
} else {
    if (StrUtil.isBlank(dto.getGrade()) || StrUtil.isBlank(dto.getClassName())) {
        throw new BusinessException("请填写你的年级和班级");
    }
}
```

**isTeacher 从 Controller 传进来**（Service 拿不到 SecurityContext）：

```java
// BlogRegistrationController
boolean isTeacher = "TEACHER".equalsIgnoreCase(SecurityContext.getRoleCode());
blogRegistrationService.submitRegistration(dto, applicantId, isTeacher);
```

> ⚠️ 改 Service 方法签名时记得**全项目搜 `submitRegistration`**，
> 调用点不止一处。本项目实测只有 Controller 一处，改完编译通过。

### 「我收到的」展示适配

老师的申请没有年级班级，原来会渲染成两个「未填」标签，空荡荡的。
现在显示橙色「**老师申请**」标签，理由那栏叫「为什么感兴趣」而不是「补充说明」。

判断方式**不用后端加字段**：

```js
// 老师申请不填这三项，所以全空就是老师申请
function isTeacherApply(item) {
  return !item.grade && !item.className && !(item.skillList || []).length
}
```

> 为什么不在 `RegistrationVO` 加 `applicantRoleCode`：数据本身就能区分，
> 加字段就要连带改 VO、Service 回填、admin 层聚合，收益为零。

## 12.3 顺手修掉的老 bug：blog 模块的业务提示全被吞掉

### 现象

验证时发现：后端明明抛了 `请填写你的年级和班级`，
**前端收到的却是「服务器开小差了，请稍后再试」**。

### 根因：项目里有两个同名的 BusinessException

```
com.qll.ucch.exception.BusinessException        （common 模块）← 全局处理器认这个
com.qll.ucch.models.common.BusinessException    （blog 模块自带）← Service 实际抛的是这个
```

blog 模块为了不把编译绑死在别的模块上，自己带了一个最简版，**它的注释里写着**
「交给 admin 层的全局异常处理器兜底」—— 但 `GlobalExceptionHandler` 只接了一个。

### 影响范围（比一开始想的大）

不只是新代码。`BlogArticleServiceImpl`、`BlogRegistrationServiceImpl` 等
**整个 blog 模块**抛的业务提示全部掉进兜底分支：

```
"不能对自己发布的内容发起对接申请"
"你已经提交过对接申请，请等待对方处理"
"该内容尚未发布，暂时无法对接"
...
```

**这些提示用户从来没看到过**，全是「服务器开小差了」。

### 修法

在 `GlobalExceptionHandler` 里补一个处理方法（两个类都直接继承 `RuntimeException`，
**没有继承关系**，所以 Spring 不会报 `@ExceptionHandler` 歧义）：

```java
@ExceptionHandler(com.qll.ucch.models.common.BusinessException.class)
public Result<Void> handleBlogBusiness(com.qll.ucch.models.common.BusinessException e,
                                       HttpServletRequest request) {
    log.warn("业务异常 [{}] {}", request.getRequestURI(), e.getMessage());
    return Result.fail(e.getCode(), e.getMessage());
}
```

### 修复验证

| | 修复前 | 修复后 |
| --- | --- | --- |
| 业务异常走 WARN 分支 | 0 次 | **4 次** |
| 掉进兜底 ERROR 分支 | **4 次** | **0 次** |

> **这个 bug 说明反向验证的价值**：如果只测「正向能提交成功」，永远发现不了它。
> 正是因为断言了「拒绝时应该给出具体提示」，才暴露出提示根本没传到前端。

# 十三、第五轮改造：头像位置 + 两个红点联动已读

## 13.1 用户反馈

> 原话：「沟通窗口里面，己方的头像应该在靠右侧而不是在文字左侧；消息中心和站内沟通的红点消息，不是同步消失的，这个能同时检测吗？目前是什么检测方式？」

## 13.2 头像位置

### 根因

长期会话页 `ChatCenter.vue` 用了 `flex-direction: row-reverse` 把整行反转：

```
DOM 顺序：[对方头像][气泡][自己头像]
row-reverse 之后：[自己头像][气泡][对方头像]   ← 自己的头像翻到了最左
```

### 改法

去掉 `row-reverse`，**DOM 顺序不动**，改用 `justify-content` 控制左右：

```css
.msg-row { justify-content: flex-start; }        /* 对方消息靠左 */
.msg-row.mine { justify-content: flex-end; }     /* 自己的靠右 -> 头像自然在文字右侧 */
```

这样对方是 `[头像][气泡]`、自己是 `[气泡][头像]`，两头贴边、中间留白，跟微信/QQ 的习惯一致。

### 临时通道页原来压根没有头像

`TmpRoom.vue` 只有一个「我 / 对方」文字标签。一并补上头像（对方靠左、自己靠右）。
自己头像的昵称从 `getUserInfo()` 拿（`authSession.js` 里已有）。

## 13.3 两个红点为什么不同步（回答"现在是什么检测方式"）

### 现状机制

| | 消息中心红点 | 站内沟通红点 |
| --- | --- | --- |
| 数据来源 | `notice_box_info.read_status` | `chat_message.read_status` |
| 前端算法 | `getUnreadCount().total` | `getSessionList()` 逐条 `unreadCount` 累加 |
| 刷新方式 | **60 秒轮询** `setInterval(loadUnread, 60000)` | 同上 |
| 已读触发 | 点单条 / 点「全部已读」 | 打开会话就整条标已读 |

### 为什么"不消失"

**这是结构性问题** —— 两个红点数的是**两张不同的表**。

读完聊天只改了 `chat_message.read_status`，而 `notice_box_info` 里那条
「收到一条新消息」（`msg_type=4`）**还挂着未读**。

加上 60 秒轮询，用户会感觉"点了没反应"。

## 13.4 改法：精确联动 + 实时刷新

### ① 自动联动已读（精确到会话）

**给通知表加关联字段**：

```sql
ALTER TABLE notice_box_info
    ADD COLUMN ref_id BIGINT NULL COMMENT '关联对象ID：msg_type=4(会话消息)时存会话ID';
CREATE INDEX idx_notice_user_type_ref ON notice_box_info (user_id, msg_type, ref_id);
```

**为什么必须精确到会话，不能按类型粗清**：

```
按类型粗清：读完 A 会话 -> 把所有 msg_type=4 的通知都清掉 -> B 会话的通知也被误清
按 ref_id：读完 A 会话 -> 只清 ref_id=A 的通知 -> B 不受影响
```

**两个方向都接上**：

```
读完某个会话        -> ChatServiceImpl.markSessionRead 里调 noticeService.markReadByRef(userId, sessionId)
消息中心"全部已读"  -> NoticeServiceImpl.markAllRead 里连带清掉 chat_message 的未读
```

### ② 实时刷新（不用等 60 秒）

建了个轻量全局信号 `utils/unreadBus.js`：

```js
export const unreadBus = reactive({ version: 0, lastReason: '' })
export function refreshUnread(reason = '') {
  unreadBus.version += 1
  unreadBus.lastReason = reason
}
```

- 任何已读操作完成后调 `refreshUnread()`
- 顶部导航 `watch(() => unreadBus.version)` 立刻重拉两个红点
- **60 秒轮询保留当兜底**（应对另一台设备操作等场景）

> **为什么不用 mitt 之类的库**：需求就是一个计数器加一次广播，
> Vue 自带的 `reactive` 够了，少一个依赖、少一份体积。

## 13.5 两个技术坑（都在本轮踩到）

### 坑1：循环依赖会导致启动失败

`ChatServiceImpl` 已经注入了 `INoticeService`（发消息要发通知）。
如果 `NoticeServiceImpl` 再注入 `IChatService`，就是**双向依赖** ——
Spring 3.x 默认禁止循环引用，**应用直接启动失败**。

**改法**：`NoticeServiceImpl` 直接用 `ChatMessageMapper`（两个 Mapper 都在 notice 模块内），
绕开 Service 层就没有循环了。

### 坑2：不能改被别的模块依赖的方法签名

`INoticeService.sendNotice` 的注释里明确写着「blog 模块在调用，签名锁死」。

**改法**：**加重载**（多一个 `refId` 参数），原签名原样保留。

```java
void sendNotice(Long userId, String title, String content, Integer msgType);            // 原样不动
void sendNotice(Long userId, String title, String content, Integer msgType, Long refId); // 新增
```

# 十四、第六轮改造：找回密码改成手机号

## 14.1 用户需求的变化过程

> 用户先说：「你注册的邮箱改成必填，因为你在找回密码的时候是需要的」
> 后又说：「或者你看看找回密码的时候能不能弄手机号找回？」

于是确认了最终口径：**找回密码走手机号，手机号注册必填，邮箱恢复选填**。

**为什么手机号比邮箱好**：

1. 手机随身带，不像邮箱那样容易忘
2. `sys_user.phone` 本来就有**唯一索引**，能唯一定位到人
3. 学生注册时手机号是真实在用的，邮箱经常随便填

**前提**：手机号必须改成**必填**。不然不填手机号的账号照样找回不了 ——
这和「邮箱必填」是同一个逻辑：**找回凭据必须人人都有**。

## 14.2 一个顺带查出并修掉的 bug

找回密码页 `ForgotPassword.vue` 提交时字段名写错了：

```js
// 改前（错的）
await findPassword({
  account: form.account,
  email: form.email,
  password: form.password        // ← 后端要的是 newPassword
})
```

后端 `ResetPasswordDTO` 的字段叫 **`newPassword`**，前端传的是 `password` ——
**这个找回密码功能从来就没成功过**（后端收到 newPassword 为 null，直接被 `@NotBlank` 拦下）。

# 十六、第八轮改造：找回密码做成「手机号 + 邮箱」双方式并行

## 16.1 口径变化

> **第六轮**：把找回密码从邮箱改成手机号（手机号注册必填）。
> **本轮**：用户说「**邮箱找回密码不要删，和手机找回做并行**」——
> 两种方式**都保留、都能用**，用户在页面上自己选。

**为什么两种都留**：

1. 用户可能只记得其中一个 —— 邮箱是注册时填的，手机是随身带的
2. 两个接口各自独立，互不影响，删一个对另一个没好处
3. 都留着是「多一条路」，不是「多一份维护负担」（代码量很小）

## 16.2 两种方式的对照

| | 手机号版 | 邮箱版 |
| --- | --- | --- |
| 接口 | `POST /user/find/pwd/phone` | `POST /user/find/pwd/email` |
| 校验凭据 | 账号 + 手机号 | 账号 + 邮箱 |
| 入参 DTO | `ResetByPhoneDTO` | `ResetPasswordDTO` |
| Service 方法 | `resetPasswordByPhone` | `resetPassword` |
| 注册时该字段 | **必填** | 选填 |
| 前端默认 | ✅ 默认选中 | 需手动切换 |

> **关键差异**：手机号是注册必填的，所以**每个账号都能用手机号找回**；
> 邮箱是选填的，没填邮箱的账号用不了邮箱版 —— 前端在邮箱模式下有提示引导改用手机号。

## 16.3 前端交互

`ForgotPassword.vue` 第一步加了「验证方式」切换：

```
○ 用手机号  ○ 用邮箱      ← 单选按钮，默认「用手机号」

账号    [_______________]
手机号  [_______________]      ← 选手机号时显示这个输入框
              （或）
邮箱    [_______________]      ← 选邮箱时显示这个输入框
⚠ 注：邮箱是注册时选填的，没填邮箱的话请改用「用手机号」

[ 下一步 ]
```

**校验规则按模式动态切换**（`rules1` 改成 `computed`）：

```js
// 没选中的那个字段是空的，如果两个规则一起校验会一直报「请输入」
if (mode.value === 'phone') {
  base.phone = [required, pattern]
} else {
  base.email = [required, type: 'email']
}
```

提交时也按模式走不同接口，但**两者都传 `newPassword`**（后端字段名就是这个）。

## 16.4 顺带处理的两件事

### ① 接口路径改名

邮箱版的路径原来是 `/find/pwd/enterprise` —— 最早是企业注册用邮箱所以这么叫，

## 16.5 ⚠️ 字段名陷阱（第二次踩）

`Profile.vue` 的「修改密码」复用找回密码接口，改的时候**又写成了 `password`**：
