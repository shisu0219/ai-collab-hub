# 四、板块 B：小组功能（本轮核心）

## 4.1 业务模型

```
一个小组 ──只有──> 一个项目（内容）
   │
   ├── 组长（1 人，即 blog_article_info.user_id）
   ├── 组员（若干学生）
   └── 指导老师（0 或 1+ 人，可后续添加）

进组方式：
   ① 组长发起邀请 → 对方同意 → 进组
   ② 管理员直接拉人 → 无需同意 → 直接进组
```

## 4.2 数据库改动

### 新增表 `blog_group`（小组表）

```sql
CREATE TABLE IF NOT EXISTS blog_group
(
    id           BIGINT PRIMARY KEY COMMENT '小组ID',
    name         VARCHAR(100) NOT NULL COMMENT '小组名称',
    article_id   BIGINT NULL COMMENT '关联的项目ID（一个小组只能有一个项目）',
    leader_id    BIGINT NOT NULL COMMENT '组长用户ID',
    intro        VARCHAR(500) NULL COMMENT '小组简介',
    -- [意见可见性] 全局默认：0仅组内 1组外可见摘要 2组外可见全部
    opinion_scope TINYINT NOT NULL DEFAULT 0 COMMENT '意见组外可见性（全局默认）',
    status       TINYINT NOT NULL DEFAULT 1 COMMENT '小组状态：1正常 0解散',
    create_time  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    create_by    BIGINT NULL,
    update_by    BIGINT NULL,
    delete_time  DATETIME NULL DEFAULT NULL,
    UNIQUE KEY uk_group_article (article_id),
    INDEX idx_group_leader (leader_id)
) COMMENT '项目小组表';
```

> `uk_group_article` 唯一索引 —— **数据库层面保证「一个小组只能有一个项目」，也保证「一个项目只属于一个小组」**。这条约束放在库里比放在代码里可靠。

### 新增表 `blog_group_member`（小组成员表）

```sql
CREATE TABLE IF NOT EXISTS blog_group_member
(
    id          BIGINT PRIMARY KEY COMMENT '主键',
    group_id    BIGINT NOT NULL COMMENT '小组ID',
    user_id     BIGINT NOT NULL COMMENT '成员用户ID',
    member_role TINYINT NOT NULL DEFAULT 2 COMMENT '成员角色：1组长 2组员 3指导老师',
    join_type   TINYINT NOT NULL DEFAULT 1 COMMENT '进组方式：1邀请同意 2管理员直接拉',
    status      TINYINT NOT NULL DEFAULT 1 COMMENT '状态：0待同意 1已加入 2已拒绝 3已退出',
    join_time   DATETIME NULL COMMENT '加入时间',
    create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    delete_time DATETIME NULL DEFAULT NULL,
    UNIQUE KEY uk_group_user (group_id, user_id),
    INDEX idx_gm_user (user_id),
    INDEX idx_gm_status (status)
) COMMENT '小组成员表';
```

**说明**
- `member_role` 三个值把「组员」和「指导老师」分开，**指导老师天然是「组内人员」**（按你的口径，组内人员能看全部意见）
- `status` 用 0/1/2/3 表达「待同意/已加入/已拒绝/已退出」—— 邀请制必须有「待同意」态
- `join_type` 区分「同意进组」和「管理员直拉」，**便于审计**（管理员拉的人是谁拉的，留痕）

### `blog_article_info` 改动

```sql
ALTER TABLE blog_article_info
    ADD COLUMN group_id BIGINT NULL COMMENT '所属小组ID' AFTER user_id;

CREATE INDEX idx_article_group ON blog_article_info (group_id);
```

`user_id` **保留不动**，其语义从「发布者」变为「组长」。
**为什么不删掉 user_id 改成只留 group_id**：
- 删字段要改 PO / DTO / VO / Service / 前端所有引用，风险大
- 保留它，查询「我的项目」时还能直接用（组长查自己组）
- `group_id` 是新增的，新老数据都能兼容

# 五、板块 C：答辩意见（本轮第二个核心）

## 5.1 先明确一个关键点：意见不是「评论」，是「答辩资料归档」

按你的原话，意见的内容是**答辩现场老师方/专业方给出的答辩问题和意见**，
由**管理员上传**，**基本是整理成文档或表格上传的**。

所以设计上要分两颗事情：

```
① 资料本体   管理员上传的文档/表格原件（Word/Excel/PDF 等）
② 结构化条目 从资料里整理出来的「问题」和「意见」，逐条存库
```

**为什么要拆开**：你说「基本是整理成文档或者表格上传」——
如果只存文档，组员得下载打开看，**没法控制单条可见性**（你要求组长能设单条覆盖）。
所以：

- **文档原件**照常存附件，组员可以下载
- **另存一份结构化条目**，每条一个可见性开关

> ⚠️ **这一点需要你再确认一下**（见第七节问题 1）：
> 是「上传文档就行、不用逐条录」，还是「上传文档 + 逐条录入条目」？
> 两者工作量差别很大。本文按「两者都支持」写，但可以做减法。

## 5.2 数据库改动

### 新增表 `blog_opinion`（答辩意见表）

```sql
CREATE TABLE IF NOT EXISTS blog_opinion
(
    id           BIGINT PRIMARY KEY COMMENT '意见ID',
    article_id   BIGINT NULL COMMENT '关联项目ID',
    group_id     BIGINT NOT NULL COMMENT '关联小组ID',
    title        VARCHAR(200) NULL COMMENT '问题/意见标题',
    content      TEXT         NOT NULL COMMENT '问题与意见正文',
    opinion_type TINYINT NOT NULL DEFAULT 1 COMMENT '类型：1答辩问题 2答辩意见 3修改建议',
    source       VARCHAR(200) NULL COMMENT '来源（自由文本，如「张老师」「校外专家」）',
    attachments  TEXT NULL COMMENT '关联资料地址列表（管理员上传的文档/表格）',
    -- 单条可见性覆盖：NULL=跟随小组全局设置 0仅组内 1组外可见摘要 2组外可见全部
    scope_override TINYINT NULL COMMENT '本条的组外可见性（覆盖全局）',
    uploader_id  BIGINT NOT NULL COMMENT '上传的管理员ID',
    create_time  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    create_by    BIGINT NULL,
    update_by    BIGINT NULL,
    delete_time  DATETIME NULL DEFAULT NULL,
    INDEX idx_op_group (group_id),
    INDEX idx_op_article (article_id)
) COMMENT '答辩意见表';
```

**设计说明**
- `source` 是**自由文本**（按你确认的「不需要精确到人」），不关联 `sys_user`
- `scope_override` 为 NULL 时跟随 `blog_group.opinion_scope`（全局默认），
  有值则覆盖 —— **正好实现你说的「可以一次设置全局，也可以设置个别的意见」**
- `attachments` 存管理员上传的答辩记录文档

## 5.3 可见性规则（核心逻辑）

这是整个改造最需要写清楚的一段：

```
组长/组员         → 全部可见（无条件）
指导老师          → 全部可见（属于「组内人员」）
管理员            → 全部可见（上传者，且后台管理需要）
────────────────────────────────────────────────
组外人员（其他学生/老师，非本组成员）
    按 scope 取值：
        0 = 仅组内     → 看不到任何意见，只看到「本项目有 N 条答辩意见（仅组内可见）」
        1 = 可见摘要   → 能看到标题 + 来源 + 前 N 字（如 50 字）+ 「登录/加入小组查看全部」
        2 = 可见全部   → 全部可见
```

**取值优先级**：`scope_override`（单条）> `blog_group.opinion_scope`（全局默认）

**「有一定程度的看不见，但也不用完全看不见」—— 就是上面的 `1 = 可见摘要`**。
默认值建议设为 `1`（可见摘要），既有一定开放性，又保护内容。

### ⚠️ 可见性过滤必须做在后端

**不能靠前端隐藏**。后端 Service 里查列表时，先判断当前登录人：
- 是不是本组成员 / 指导老师 / 管理员 → 返回全部
- 否则 → 按 `scope` 裁字段（摘要模式只返回 `title` + `source` + 截断的 `content`）

**这是安全边界，前端藏按钮不算。** 前端只负责「按后端给的字段渲染」。

# 七、还需要你确认的（4 个）

## 1. 答辩意见的录入方式（影响工作量最大）

你说「基本是整理成文档或者表格上传的」。那是：

- **A. 只传文档** —— 管理员传 Word/Excel，组员下载看。
  **优点**：实现简单。**缺点**：没法控制单条可见性（你要的「单条覆盖」做不到）
- **B. 传文档 + 逐条录入** —— 文档存档，同时把关键问题/意见逐条录进系统。
  **优点**：能单条控可见性、能被通知、以后能做统计。
  **缺点**：管理员录入工作量大
- **C. 传文档 + 从表格自动导入** —— 管理员按模板整理成 Excel 后上传，
  系统读出每一行变成一条意见。
  **优点**：兼顾两者，管理员不用手工一条条敲。
  **缺点**：要定一个 Excel 模板格式

**我推荐 C**（工作量中等，但最省人力），或者 A（如果这轮只求先跑通）。

## 3. 一个学生能不能同时属于多个小组？

按「一个小组一个项目」推断，一个学生**可能**同时参与多个项目。

## 4. 组外可见性的默认值
