# 09 功能-文件映射与改造指南

> 写给要**大改这个项目**的人。
> 本文不列文件清单（那个看 `08-文件功能对照表.md`），只回答一个问题：
> **我要改某个功能，得动哪几个文件、按什么顺序改、改完怎么验证。**
>
> 所有链路都是从代码里实读出来的（接口路径、方法名、表名都经过核对）。

# 零、先搞清楚这东西到底是什么

## 一句话

**一个校园版「校内双创协作平台」**：学生 / 老师 / 管理员三端（企业端已彻底删除）
以**小组**为单位填写项目、需求、课程，平台管理员审核后公开，
其他人浏览、申请对接，双方通过站内会话沟通。
**答辩时老师方/专业方给出的问题和意见，由管理员上传，按小组可见性展示。**

## 三条业务主线

```
主线 1：注册 → 审核 → 能登录
   注册(学生/老师) → 待审状态 → 管理员审核 → 通过后能登录
   ⚠️ 未审核账号登不进去

主线 2：填写 → 审核 → 公开可见
   填写内容(项目/需求/课程) → 待审 → 管理员审核 → 通过后进公开列表
   ⚠️ 未审核内容别人看不到

主线 3：浏览 → 申请 → 沟通
   看到内容 → 发起对接申请(带理由+联系方式) → 组长通过 → 自动建会话 → 聊
   ⚠️ 不能申请自己填写的内容
```

这三条线就是整个系统的骨架。**改任何功能前，先想清楚它挂在哪条线上。**

## 一次请求的完整流转（记住这个模型，改代码不会迷路）

以「学生登录」为例：

```
Login.vue          点登录 → 调 auth.js 的 loginStudent
   ↓
api/auth.js        POST /user/login/student
   ↓
request.js         拦截器带上 token（如果有）
   ↓
【网络】→ 28848 后端
   ↓
AuthInterceptor    检查是否需要登录（登录接口有 @IgnoreAuth，直接放行）
   ↓
AuthController     收参数，转给 Service
   ↓
SysUserServiceImpl.doLogin()   ← 真正干活：查库、比密码、生成 JWT
   ↓
SysRoleService     查这个用户的角色
   ↓
返回 LoginVO       { roleCodes:["ADMIN"], tokenInfo:{ token:"eyJ..." } }
   ↓
Login.vue         读 data.tokenInfo.token 存起来，按角色跳转
   ↓
authSession.js    写 localStorage
   ↓
router/index.js   路由守卫读 localStorage 判权限
```

**明白这条链，就知道改功能时该在哪一层动手**：

| 想改什么 | 动的层 |
| --- | --- |
| 页面长什么样、字段怎么摆 | 前端 `.vue` |
| 接口地址、传参格式 | 前端 `api/*.js` + 后端 Controller |
| 业务规则（谁能干什么、流程怎么走） | 后端 Service 实现 |
| 数据存什么、多一个字段 | SQL + PO + DTO/VO + Mapper |
| 谁能访问、免不免登录 | `@IgnoreAuth` 注解 + `router/index.js` 守卫 |

# 一、跨层通用规律（最重要，先看这个）

改功能基本都在改这**六层**。一个完整的功能改动，六层都要过一遍：

```
① 数据库      sql/ai_collab_hub.sql          → 表结构、字段
② 实体层      models/po/Xxx.java             → 跟表一一对应
③ 传参层      models/dto/XxxDTO.java         → 前端传进来的东西
④ 返回层      models/vo/XxxVO.java           → 返回给前端的东西
⑤ 业务层      service/impl/XxxServiceImpl    → 真正的规则和流程
⑥ 接口层      openapi/**/XxxController       → HTTP 入口，只做转发
```

前端对应三层：

```
⑦ 接口封装    src/api/xxx.js                 → 定义后端地址
⑧ 页面        src/views/**/Xxx.vue           → 界面和交互
⑨ 路由        src/router/index.js            → 路径和权限
```

**大改时最容易漏的是 ② 和 ④** —— 改了表加了字段，PO 和 VO 没加，编译能过，
但字段永远是 null。这是本项目真实踩过的坑（详见 08 文档的附录）。

# 二、按功能模块拆解：改什么动哪里

## 2.1 登录 / 认证

**涉及文件（完整链路）**

| 层 | 文件 |
| --- | --- |
| 页面 | `views/auth/Login.vue` |
| 接口封装 | `api/auth.js` |
| 路由守卫 | `router/index.js`（`beforeEach`） |
| 登录态存储 | `utils/authSession.js` |
| 接口层 | `openapi/user/AuthController.java`（`/user/login/*`） |
| 业务层 | `sys/service/impl/SysUserServiceImpl.java` → `doLogin()` + `loginByXxx()` |
| 返回体 | `sys/models/vo/LoginVO.java`、`TokenInfoVO.java` |
| 传参 | `sys/models/dto/StudentLoginDTO.java` 等 4 个 |
| 认证机制 | `security/AuthInterceptor.java`、`JwtUtil.java`、`IgnoreAuth.java` |
| 角色常量 | `sys/constant/SysConstants.java` |

**关键设计（改之前必须知道）**

1. **四种角色共用一套登录逻辑**。`SysUserServiceImpl` 里有 4 个入口方法
   （`loginByStudent` / `loginByTeacher` / `loginByAdmin`），
   但它们都调用同一个私有方法 `doLogin()`，只是传入不同的 `expectRoleCode`。
   **要加第 5 种角色，只需加一个入口方法，别复制粘贴整个登录逻辑。**

2. **token 藏在 `tokenInfo` 里，顶层没有**。
   ```json
   { "roleCodes": ["ADMIN"], "tokenInfo": { "token": "eyJ..." } }
   ```
   前端必须读 `data.tokenInfo.token`。**改成顶层平铺会一次性弄坏所有登录跳转。**

3. **角色字段是数组**：`roleCodes` / `roleNames` 都是数组，不是单个值。
   前端 `authSession.js` 的 `getRoleCode()` 取 `[0]`。

4. **登录入口不卡角色**。选错身份卡片只会记日志，不会拦你。
   真正的权限控制靠「库里角色 + 前端路由守卫」。
   **别把入口改回成权限闸门** —— 那会产生「账号密码都对却进不去」的 bug。

**改这里的典型任务**

| 任务 | 要动 | 不要动 |
| --- | --- | --- |
| 加第 4 个角色（比如「校外导师」） | SQL 加角色行 → `SysConstants` 加常量 → 加 DTO → Service 加 `loginByXxx` + `registerXxx` → Controller 加接口 → `api/auth.js` → `Login.vue` 加卡片 → `roleDisplay.js` 加映射 | 不要动现有 4 个角色的任何分支 |
| 改登录页样式 | 只动 `Login.vue` | 不要动 `authSession.js` / 后端 |
| 换成 OAuth / 短信登录 | `AuthController` + `SysUserServiceImpl.doLogin` + `JwtUtil` | 前端改动很少 |

## 2.2 注册与账号审核

**涉及文件**

| 层 | 文件 |
| --- | --- |
| 页面 | `views/auth/Register.vue`（用户注册）、`views/admin/AccountReview.vue`（管理员审核） |
| 接口封装 | `api/auth.js`（注册）、`api/admin.js`（审核） |
| 接口层 | `openapi/user/AuthController.java`（`/register/*`）、`openapi/user/UserReviewController.java`（`/user/review/*`） |
| 业务层 | `SysUserServiceImpl.doRegister()`、`SysUserReviewServiceImpl.java` |
| 传参 | `StudentRegisterDTO` / `TeacherRegisterDTO` / `UserAuditDTO` |
| 返回体 | `UserReviewVO.java` |
| 表 | `sys_user`（`audit_status` 字段）、`sys_user_review` |

**关键设计**

1. **注册后不能直接登录**。`sys_user.audit_status` 默认 0（待审），
   登录时校验这个字段，未通过就拒绝。**这是注册审核制的核心。**

2. **老师注册比学生多两个字段**（`department` 院系、`title` 职称），
   但**这两个字段没有独立建表**，是拼成字符串塞进 `sys_user_review.credentials` 的：
   ```
   院系：人工智能学院；职称：副教授；材料：教师资格证.pdf
   ```
   展示时由 `SysUserReviewServiceImpl.splitCredentials()` 拆开。
   **要给老师加更多注册字段，得先决定是继续拼字符串还是真建表。**

3. **审核通过要写两处**：`sys_user_review`（审核记录）+ `sys_user.audit_status`（账号状态）。
   改审核逻辑时两个都要管，只改一个会出现「审核记录说通过了但账号还是待审」。

**改这里的典型任务**

| 任务 | 要动 |
| --- | --- |
| 加注册字段（如学号） | SQL 加列 → `StudentRegisterDTO` → `SysUserServiceImpl.doRegister` → `SysUser.java` PO → `Register.vue` 表单 |
| 改审核流程（加二级审核） | `SysUserReviewServiceImpl` → 加状态枚举 → `sys_user_review` 加字段 → `AccountReview.vue` |
| 注册后自动通过 | 改 `doRegister` 里 `audit_status` 的初值 |

## 2.2.5 项目小组（最新一轮新增）

**涉及文件（完整链路）**

| 层 | 文件 |
| --- | --- |
| 页面（用户端） | `views/cooperation/MyGroup.vue`（建组、成员、邀请、可见性设置） |
| 页面（管理端） | `views/admin/GroupManage.vue`（全部小组、代建、直接拉人） |
| 接口封装 | `api/group.js` |
| 接口层 | `openapi/blog/BlogGroupController.java`（`/blog/group/*`） |
| 业务层 | `blog/service/impl/BlogGroupServiceImpl.java` |
| 接口 | `blog/service/IBlogGroupService.java` |
| 实体 | `blog/models/po/BlogGroup.java`、`BlogGroupMember.java` |
| 传参 | `GroupSaveDTO`、`GroupMemberInviteDTO`、`GroupMemberHandleDTO` |
| 返回 | `GroupVO`、`GroupMemberVO` |
| 表 | `blog_group`、`blog_group_member`；`blog_article_info.group_id` |
| 菜单/路由 | `CooperationLayout.vue`、`AdminLayout.vue`、`router/index.js` |

**关键设计（改之前必须知道）**

1. **一个小组只能有一个项目** —— 库里 `blog_group.article_id` 上有 `uk_group_article` 唯一索引。
   **改这块别只在代码里判断**：库层面卡死才是可靠的，代码判只是为了报错好看。

2. **`blog_article_info.user_id` 的语义是「组长」**，字段名没改（改它会牵连 PO/DTO/VO/前端一大片），
   但含义变了。**看到 `userId` 不要以为是「随便一个发布者」。**

3. **组长自己也有一条成员记录**（`member_role=1`）。
   这样「判断某人是否组内成员」只需查一张表，不用到处特判「是不是组长」。

4. **两种进组方式，语义不同**：
   - `join_type=1`：组长邀请 → 对方**必须同意**（记录先落 `status=0待同意`）
   - `join_type=2`：**管理员直接拉** → 免同意，直接 `status=1`
   区别在权限：**管理员能跳过同意，组长不能。**

5. **重复邀请不新增记录，改状态** —— 表上有 `uk_group_user` 唯一索引，硬插会报错。
   实现见 `addMemberRow()`：先查再决定 insert 还是 update。

6. **组长不能被移除**，要换人走 `transferLeader`（老组长降为组员 + 新组长升上去，两步都做）。

**改这里的典型任务**

| 任务 | 要动 |
| --- | --- |
| 加成员角色（如「指导老师」） | `blog_group_member.member_role` 加值 → `memberRoleName()` 映射 → 前端角色显示 |
| 一个组允许多个项目 | **要去掉 `uk_group_article` 唯一索引** + 改 `bindArticle` 的校验 + 前端「一个组一个项目」的文案 —— 这是个结构性改动，别小看 |
| 换组长流程要审批 | `transferLeader` 加状态字段 + 通知 |
| 学生同时加入的组数限制 | `createGroup` / `inviteMembers` 里加校验 |

## 2.2.6 答辩意见（最新一轮新增）

**涉及文件（完整链路）**

| 层 | 文件 |
| --- | --- |
| 页面（管理端） | `views/admin/OpinionManage.vue`（上传、批量导入、可见性、删除） |
| 组件（用户端） | `components/OpinionList.vue`（挂在 `MyGroup.vue` 和 `ProjectDetail.vue` 里） |
| 接口封装 | `api/opinion.js` |
| 接口层 | `openapi/blog/BlogOpinionController.java`（`/blog/opinion/*`） |
| 业务层 | `blog/service/impl/BlogOpinionServiceImpl.java` |
| 接口 | `blog/service/IBlogOpinionService.java` |
| 实体 | `blog/models/po/BlogOpinion.java` |
| 传参 | `OpinionSaveDTO`、`OpinionImportRowDTO`、`OpinionScopeDTO` |
| 返回 | `OpinionVO` |
| 表 | `blog_opinion`；可见性全局默认在 `blog_group.opinion_scope` |

**关键设计（这块最容易改错）**

1. **可见性过滤必须在后端 Service，不能靠前端隐藏。**
   实现集中在 `BlogOpinionServiceImpl` 的两个方法：
   - `resolveScope(op, group)` —— 算一条最终生效的可见性：**单条覆盖 > 全局默认**
   - `convert()` / `toVO()` —— 按身份裁剪：组外+仅组内**直接过滤掉**；摘要档**截断正文且不下发附件**
   列表和详情走同一套逻辑，改的时候**两个入口都要顾及**。

2. **摘要档不下发附件地址**。否则「正文截断」白做 —— 直接下载资料就绕过限制。

3. **上传人昵称由 admin 层回填**（blog 模块依赖不到 sys 模块）——
   所以 `OpinionVO` 里有 `uploaderId`（回填用，前端不显示）。

4. **批量导入走 CSV**，前端解析后提交数组。
   用 CSV 不用 xlsx 是因为**前端不用引解析库**（xlsx 包体积大），
   而 Excel/WPS 都能「另存为 CSV」，管理员成本一样。

5. **上传后给组内全体发通知**，照 `BlogArticleServiceImpl.sendNoticeQuietly()` 的模式 ——
   **发通知失败只记日志，不能让上传主流程失败。**

**⚠️ 一个必须记住的坑**

改「恢复跟随全局设置」这类**把字段清空**的操作时，**不能用 `setXxx(null)` + `updateById()`** ——
MyBatis-Plus 默认字段策略是 NOT_NULL，**null 字段根本不进 SQL，操作静默失效**
（接口返回 200、日志也打了，但库里没变）。必须用 `UpdateWrapper` 显式 `.set()`：

```java
baseMapper.update(null, new LambdaUpdateWrapper<BlogOpinion>()
        .eq(BlogOpinion::getId, opinionId)
        .set(BlogOpinion::getScopeOverride, scope)   // null 也能写进去
        .set(BlogOpinion::getUpdateBy, operatorId));
```

**改这里的典型任务**

| 任务 | 要动 |
| --- | --- |
| 改摘要截断字数 | `BlogOpinionServiceImpl.SUMMARY_LENGTH` |
| 加意见类型（如「答辩评分」） | `opinion_type` 加值 → `typeName()` 映射 → 前端下拉与显示 |
| 加「意见回复/讨论」 | 需要新表或加 `parent_id`（`blog_opinion` 目前没有） |
| 意见要关联真实账号 | 现在 `source` 是自由文本；要改成关联需加 `source_user_id` + 选人组件 |
| 视频支持 | 见 `11-…改造记录.md` 第八节（字段已预留） |

## 2.2.7 申请表单（最新一轮改造）

**涉及文件（完整链路）**

| 层 | 文件 |
| --- | --- |
| 页面 | `views/cooperation/ProjectDetail.vue`（申请弹窗）、`MyApplications.vue`（组长审核时看申请人信息） |
| 接口封装 | `api/blog.js`（提交申请）、`api/meta.js`（表单选项） |
| 接口层 | `openapi/blog/BlogRegistrationController.java`、`openapi/blog/ApplyMetaController.java` |
| 业务层 | `blog/service/impl/BlogRegistrationServiceImpl.java` |
| 实体 | `blog/models/po/BlogRegistration.java` |
| 传参/返回 | `RegistrationSubmitDTO`（grade/className/skills）、`RegistrationVO`（含 `skillList`） |
| 表 | `blog_registration`（`grade` / `class_name` / `skills`） |

**关键设计**

1. **年级/班级/技能是硬编码的固定值**，在 `ApplyMetaController` 里。
   **为什么不建字典表**：学校层面固定值、一年顶多变一次，硬编码比建表省事，
   也避免「字典表被清空导致下拉框空白」的事故。**改就改那一个文件。**

2. **班级随年级联动** —— 不同年级的班级不是一套，返回的是 `Map<年级, List<班级>>`，
   前端选完年级再筛。

3. **技能存 code 不存中文名** —— 以后改显示名不会把历史数据搞乱。

4. **这四个字典接口都免登录**（`@IgnoreAuth`）。不加的话，用户「看到内容想申请」时
   还得先登录才看得到下拉选项。

5. **校验放 Service 不做 DTO 注解** —— 因为要给具体提示（「请填写你的年级和班级」），
   而不是笼统的参数错误。

**改这里的典型任务**

| 任务 | 要动 |
| --- | --- |
| 加年级（如 27级） | `ApplyMetaController.GRADES` 加一项 |
| 加班级 | `ApplyMetaController.CLASS_MAP` |
| 加技能 | `ApplyMetaController.SKILLS` 加一项（code + name） |
| 联系方式改回必填 | `RegistrationSubmitDTO` 加校验 + `ProjectDetail.vue` 的 `applyRules` |
| 申请要带附件 | 表已有 `attachments` 字段，加前端上传控件即可 |

## 2.2.8 临时沟通通道（最新一轮新增）

**涉及文件（完整链路）**

| 层 | 文件 |
| --- | --- |
| 页面 | `views/cooperation/TmpRoom.vue`（聊天页，路由 `/tmp-room/:token`） |
| 入口 | `views/cooperation/MyApplications.vue`（「临时通道」按钮） |
| 接口封装 | `api/tmpRoom.js` |
| 接口层 | `openapi/notice/TmpRoomController.java`（`/tmp/room/*`） |
| 业务层 | `notice/service/impl/TmpRoomServiceImpl.java` |
| 实体 | `notice/models/po/TmpRoom.java`、`TmpRoomMessage.java` |
| 传参/返回 | `TmpRoomCreateDTO`、`TmpRoomMessageSendDTO`、`TmpRoomVO`、`TmpRoomMessageVO` |
| 表 | `tmp_room`、`tmp_room_message` |
| 自动开通 | `BlogRegistrationServiceImpl.handleRegistration()` 通过时调 `openTmpRoomQuietly` |

**和站内会话的区别（别搞混）**

| | `chat_session` 站内会话 | `tmp_room` 临时通道 |
| --- | --- | --- |
| 入口 | 登录后「站内沟通」列表 | **链接** `/tmp-room/{token}` |
| 生命周期 | 一直在 | **有有效期（默认72h），到期自动失效** |
| 访问 | 必须登录 | **凭链接可看，发言才要登录** |

**两套并存、互不影响。** 不要试图合并 —— 语义不同（正式合作 vs 先聊聊看）。

**⚠️ 改这块必须记住的三条**

1. **token 用 `SecureRandom` 生成 24 字节再 Base64（URL 安全字符集）。**
   **别改成自增ID或时间戳拼的** —— 那等于把房间大门敞开。

2. **判断房间可用必须 `status` + `expireTime` 一起看。**
   ```java
   // status=0 是手动关的（可能还没到点）；expireTime<now 是到点失效的（status 可能还是 1）
   // 只看一个就会漏。统一走 requireUsableRoom()，别在别处另写一套判断。
   ```
   改可用性逻辑时，**所有入口都要跟着改**（`enter` / `messages` / `sendMessage` 都调它）。

3. **免登录的接口必须显式标 `@IgnoreAuth`。**

## 2.2.12 未读红点与联动已读（踩过坑）

### 两个红点的数据来源

| 红点 | 数据来源 | 前端算法 |
| --- | --- | --- |
| 消息中心 | `notice_box_info.read_status` | `getUnreadCount().total` |
| 站内沟通 | `chat_message.read_status` | `getSessionList()` 逐条 `unreadCount` 累加 |

**它们是两张表、两条独立的数据流** —— 所以「不同步」不是 bug，是结构使然。

### 联动的实现（靠 refId）

```
notice_box_info.ref_id   会话消息(msg_type=4) 存会话ID；其它类型留空
```

| 场景 | 谁做 | 调什么 |
| --- | --- | --- |
| 读完某个会话 | `ChatServiceImpl.markSessionRead` | `noticeService.markReadByRef(userId, sessionId)` |
| 消息中心「全部已读」 | `NoticeServiceImpl.markAllRead` | 直接更新 `chat_message` |

**为什么不能用 `msg_type=4` 粗清**：那会把**其它会话**的通知也清掉。
必须靠 `ref_id` 精确匹配。

### 实时刷新（不用等 60 秒轮询）

`utils/unreadBus.js`：一个 `reactive` 版本号 + `refreshUnread()` 广播。

```
已读操作完成 -> refreshUnread() -> 版本号+1
CooperationLayout watch(version) -> 立刻重拉两个红点
```

**60 秒轮询保留当兜底**（另一台设备操作等场景）。

> 加新的已读入口时，记得**操作完成后调一次 `refreshUnread()`**，
> 否则红点要等一分钟才更新。

### ⚠️ 三个必须避开的坑

**1. 循环依赖会启动失败**

`ChatServiceImpl` 已注入 `INoticeService`。
`NoticeServiceImpl` 若再注入 `IChatService` → 双向依赖 → **Spring 3.x 启动直接失败**。

**改法**：`NoticeServiceImpl` 注入 `ChatMessageMapper`（同模块的 Mapper），绕开 Service 层。

**2. 别改被别的模块依赖的方法签名**

`INoticeService.sendNotice` 注释里写着「blog 模块在用，签名锁死」。
**加重载**，别改原签名。

**3. 头像布局别用 `row-reverse`**

```css
/* 错：整行反转，自己的头像翻到最左 */
.msg-row.mine { flex-direction: row-reverse; }

/* 对：DOM 顺序不动，靠 flex-end 推右边 -> 头像自然在文字右侧 */
.msg-row.mine { justify-content: flex-end; }
```

## 2.2.13 找回密码（两种方式并行）与「必填凭据」的改动清单

### 两种方式并行，任选其一

| 方式 | 接口 | 校验凭据 | 注册时该字段 | 前端 |
| --- | --- | --- | --- | --- |
| 手机号 | `POST /user/find/pwd/phone` | `account` + `phone` → `newPassword` | **必填** | 默认选中 |
| 邮箱 | `POST /user/find/pwd/email` | `account` + `email` → `newPassword` | 选填 | 手动切换 |

两个接口都是 `@IgnoreAuth`（没登录才需要找回）。

**前端切换**：`ForgotPassword.vue` 用 `mode`（`'phone'` / `'email'`）控制显示哪个输入框、走哪个接口。

> ⚠️ **`rules1` 必须写成 `computed`**：两个字段的校验规则都定义着，但只校验当前选中的那个。
> 写成普通对象的话，没选中的字段是空的，会一直报「请输入」。

### ⚠️ 坑1：字段名前后端要对齐

```
前端提交：  { account, phone, newPassword }
后端 DTO：                  ^^^^^^^^^^^ 必须是 newPassword
```

老页面写的是 `password` —— **功能从来没成功过**。
改这类页面时，**对着 DTO 逐字核字段名**，别凭手感写。

**这个坑踩过两次**：一次在 `ForgotPassword.vue`（第六轮修），
一次在 `Profile.vue` 的「修改密码」（第八轮修，也是复用这个接口）。

### ⚠️ 坑2：找回凭据对应的字段必须是必填

这是**因果关系**，不是巧合：

```
找回密码靠「账号 + 手机号」验证身份
=> 手机号必须人人都有 => 注册时手机号必须必填
```

**为什么手机号必填、邮箱选填**：

- 手机号是**主要**找回方式（人人都有，保证任何账号都能找回）
- 邮箱是**备选**（记得邮箱的人多一条路，没填的走手机号）

如果哪天手机号改成选填了，没填的人就永远找回不了 —— **要动注册必填规则，先想清楚这条链**。

**改找回方式时的完整清单**（少一处就出问题）：

| # | 位置 | 改什么 |
| --- | --- | --- |
| 1 | 数据库 | 确认凭据字段**有唯一索引**（`phone` 有，`email` 有） |
| 2 | 数据库 | 现有账号**补上凭据值**（NULL 的账号找回不了） |
| 3 | 后端 DTO | 新建或修改入参；凭据格式用 `@Pattern` 校验 |
| 4 | 后端 Service | 实现校验 + 改密码；**账号不存在和凭据不对返回同一句提示**（防账号探测） |
| 5 | 后端 Controller | 新接口标 `@IgnoreAuth`；老接口保留兼容 |
| 6 | 注册 DTO | 凭据字段加 `@NotBlank`；正则**去掉 `^$|`**（那是允许空的写法） |
| 7 | 前端注册页 | 加 required + 占位提示说明用途 |
| 8 | 前端资料页 | 同上，保持一致 |
| 9 | 前端找回页 | 换字段、换 API；**对齐后端字段名** |
| 10 | 前端 api | 加新函数；老的标注「已弃用但保留」 |

# 三、改了东西之后怎么验证（不要跳）

## 3.1 三层验证链

```
第 1 层：能不能编译
   后端：mvn clean package -DskipTests    → 看 BUILD SUCCESS + EXIT=0
   前端：npm run build                    → 看 EXIT=0
   ⚠️ 这一层过了不代表功能对，本项目 7 个运行时 bug 全部逃过了编译

第 2 层：静态扫描（编译查不出来、只有真人打开才发现的）
   · 图标「用了但没 import」→ 整页白屏，build 不报错
   · 前端引用了后端不存在的字段 → 显示空白，不报错
   · 角色显示用了三元表达式 → 新角色显示成老角色，不报错
   这三个扫描脚本在 skill 里（scan_icon_imports.py / scan_role_ternaries.py）

第 3 层：真启动打接口
   起 MySQL + Redis → 起后端 → curl 打接口
   ⚠️ 必须断言「关键字段非空」，不能只看 code == 200
   ⚠️ 必须做反向验证（传错误形态，确认被拒绝）
```

## 3.2 改完必须回归的老功能

**加了新角色之后，一定要用老角色各登一遍。** 本项目踩过：
加老师角色后，二元三元表达式让老师和管理员在 4 个页面上全显示成「学生」。

## 3.3 常见「改完没生效」

| 现象 | 原因 |
| --- | --- |
| 改完前端源码、页面行为不变 | Vite HMR 图失效，重启 dev + 清 `node_modules/.vite` |
| `mvn clean` 报删不掉日志 | java 进程还占着日志文件，先 `taskkill //F //PID` 杀干净 |
| 报模块 jar 找不到 | 有两个 Maven 在并行跑，串行执行 |

# 四、大改的行动建议

1. **先明确改的是哪条业务线**（注册审核 / 填写审核 / 对接沟通 / 小组 / 答辩意见），
   顺着第二节找到对应模块，再看它列出的六层文件。

2. **SQL 先动**。加字段从 `sql/ai_collab_hub.sql` 开始，然后 PO，
   再 DTO/VO，最后 Service —— 顺序反了会编译不过，来回折腾。

3. **跨模块取数别破坏依赖链**。依赖方向是单向的：
   ```
   common → integration → notice → blog → admin
                         ↘ security ↗
   ```
   业务模块之间不能互相依赖。**要拿别的模块的数据，在 admin 层（Controller）补**。
   本项目两处都是这么处理的：注册申请人昵称、会话对方昵称。

4. **别往 DTO 上加 `@NotNull`**，如果那个字段设计成「前端可不传、后端补全」。

5. **公共函数改一处，全站生效**。这几个是公共的，改之前要想清楚影响面：
   - `utils/authSession.js` —— 全站登录态
   - `utils/roleDisplay.js` —— 全站角色显示
   - `api/request.js` —— 全站请求拦截
   - `security/AuthInterceptor.java` —— 全站鉴权

# 八、动代码前必读的几条铁律

1. **接口全部写在 admin 模块**，业务逻辑在业务模块。别在 blog 里写 Controller。
2. **业务模块之间不能互相依赖**，跨模块取数在 admin 层补。
3. **前端 ID 一律 `String()` 包一层** —— 雪花 ID 19 位，JS 数字会丢精度。
4. **前端引用后端字段前先 grep 后端确认字段真存在** —— 项目里出现过凭空发明字段。
5. **角色显示统一走 `roleDisplay.js`**，不要写 `? 'A' : 'B'` 三元表达式。
6. **DTO 上别加 `@NotNull`**，如果该字段设计成后端补全。
7. **改完必须回归老角色、老功能** —— 编译通过 ≠ 功能没坏。
