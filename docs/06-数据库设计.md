## 二、核心表结构

### sys_user（系统用户）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 主键（雪花ID） |
| account | VARCHAR(64) | 账号，唯一，至少 4 位 |
| password | VARCHAR(255) | BCrypt 加密后的密码 |
| email | VARCHAR(128) | 邮箱，唯一，**选填** |
| phone | VARCHAR(20) | 手机号，唯一，**注册必填**（找回密码要用） |
| nickname | VARCHAR(64) | 昵称/姓名 |
| avatar | TEXT | 头像地址 |
| enable | TINYINT(1) | 1 启用 / 0 禁用 |
| audit_status | TINYINT | 0 待审 / 1 通过 / 2 拒绝 |
| create_time / update_time | DATETIME | 创建/更新时间 |
| create_by / update_by | BIGINT | 创建人/更新人 |
| delete_time | DATETIME | 逻辑删除，非空表示已删 |

**索引**：account（唯一）、email（唯一）、phone（唯一）、audit_status、enable

> **email 可空**：MySQL 唯一索引允许多个 NULL，所以多人不填邮箱不冲突。
> **phone 必填**：手机号是**主要**找回方式，不填就没法用手机号找回。
>
> **两种找回方式**（详见 `11` 第十六节）：
> ```
> 手机号版：账号 + 手机号  ->  POST /user/find/pwd/phone   注册必填，人人可用
> 邮箱版：  账号 + 邮箱    ->  POST /user/find/pwd/email   注册选填，记得邮箱的人用
> ```

| progress_id | BIGINT | 进度ID |
| attachments | TEXT | 附件地址（逗号分隔） |

### blog_registration（对接申请）

学生对内容「感兴趣」时提交的申请。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 主键 |
| article_id | BIGINT | 申请的内容ID |
| user_id | BIGINT | 申请人用户ID |
| **grade** | VARCHAR(32) | **年级（新增，学生必填）** |
| **class_name** | VARCHAR(64) | **班级（新增，学生必填）** |
| **skills** | VARCHAR(255) | **擅长部分（新增，学生必填，逗号分隔的技能码）** |
| reason | VARCHAR(500) | 补充说明（选填）/ 老师填「为什么感兴趣」（老师必填） |

> **按角色分两套必填**：学生必填「年级 + 班级 + 擅长」，老师必填「为什么感兴趣」（存 `reason`）。

### blog_opinion（答辩意见）【新增】

### tmp_room（临时沟通通道）【新增】

申请通过后自动开通，凭 token 免登录查看，有有效期。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 主键 |
| **room_token** | VARCHAR(64) | **访问令牌，唯一索引。凭它免登录进房间** |
| registration_id | BIGINT | 来源对接申请ID |
| article_id | BIGINT | 关联内容ID |
| user_a / user_b | BIGINT | 双方用户ID |
| title | VARCHAR(200) | 通道标题 |
| status | TINYINT | 1 有效 / 0 已关闭 |
| **expire_time** | DATETIME | **到期时间（默认开 72 小时）** |
| create_time / update_time | DATETIME | 创建/更新时间 |

> **和站内会话的区别**：临时通道凭链接进、有有效期、外部人可看不可发；
> 站内会话要登录、长期存在、只有双方能看。

### notice_box_info（消息盒）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 主键 |
| user_id | BIGINT | 接收人用户ID |
| title | VARCHAR(200) | 消息标题 |
| content | TEXT | 消息内容 |
| **msg_type** | TINYINT | **1 审核结果 / 2 收到申请 / 3 系统通知 / 4 会话消息** |
| read_status | TINYINT(1) | 0 未读 / 1 已读 |
| **ref_id** | BIGINT | **关联对象ID。会话消息（msg_type=4）存会话ID，用于两个红点联动已读** |
| create_time / update_time / create_by / update_by / delete_time | | 同 sys_user |

**索引**：user_id、read_status、**(user_id, msg_type, ref_id)**（联动已读用）

> **为什么需要 ref_id**：消息中心和站内沟通的红点数的是**两张表**
> （`notice_box_info.read_status` / `chat_message.read_status`）。
> 有了 ref_id 才能做到「读完 A 会话只清 A 的通知」，不误伤其它会话。

## 三、表关系（主要外键关系，逻辑关联非物理外键）

```
sys_user ──1:N──> blog_article_info         （一个用户发多条内容）
sys_user ──N:M──> sys_role                  （经 sys_user_role）
sys_user ──1:N──> sys_user_review           （注册审核记录）

blog_article_info ──1:N──> blog_registration    （一条内容收到多个申请）
blog_article_info ──1:1──> blog_group           （一个小组一个内容，唯一索引约束）
blog_group ──1:N──> blog_group_member           （小组成员）
blog_group ──1:N──> blog_opinion                （小组的答辩意见）

blog_registration ──1:1──> chat_session         （一个申请开一个长期会话）
blog_registration ──1:1──> tmp_room             （申请通过自动开临时通道）

chat_session ──1:N──> chat_message
tmp_room ──1:N──> tmp_room_message
```

## 六、设计说明

### 为什么用雪花ID不用自增

分模块部署时不用抢数据库自增锁，插入性能更好；ID 本身不暴露业务量。
后端已全局把 Long 转字符串返回（`JacksonConfig`），因为雪花 ID 有 19 位，
JS 的 Number 精度不够，前端会算错。

### 为什么用逻辑删除

`delete_time` 非空表示已删，数据还在表里。答辩意见、审核记录这类要留痕，
物理删了就查不到了。

### 为什么对接申请和会话分开建表

语义不同：申请是「一次意向」，会话是「一段持续沟通」。
一个申请可能对应站内会话 + 临时通道两条沟通链，混在一张表里没法表达。

### 为什么解答辩意见要拆两层可见性

`blog_group.opinion_scope` 是组长设的**全局默认**（方便一次设完）；
`blog_opinion.scope_override` 是**单条覆盖**（某条特别敏感的可以单独设成仅组内）。
`scope_override` 为 NULL 表示跟随全局 —— 所以它必须可空，不能给默认值。

### 为什么临时通道的消息不记已读

外部访客凭链接进来，没有账号，记不了「谁读过」。
站内会话才有已读状态，因为双方都是登录用户。

### 为什么企业相关的表和角色删掉了

平台定位是**校内**双创平台，对外只有学生 / 老师 / 管理员三端。
企业端的代码和数据已全部移除，避免维护两套用不上的逻辑。
